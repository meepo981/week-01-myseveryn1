# ADR-001: Курсорна пагінація каталогу подій

**Статус:** Прийнято  
**Дата:** 2026-10-25

## Контекст

У системі EventHub користувачі переглядають каталог подій, які постійно додаються та оновлюються організаторами.

Проблема виникає, коли користувач переглядає каталог, а організатор додає нову подію між завантаженням двох сторінок.

Наприклад:

1. Користувач відкриває першу сторінку з 10 подіями.
2. Організатор додає нову подію, яка потрапляє на початок списку.
3. Користувач переходить на другу сторінку.
4. При використанні offset-пагінації одна з подій може відобразитися повторно, оскільки позиції елементів змінилися.

Необхідно забезпечити стабільний перегляд каталогу навіть під час додавання нових подій.

## Розглянуті варіанти

### Варіант 1. Offset-пагінація

Використання параметрів `limit` та `offset`.

Переваги:
- Проста реалізація.
- Можливість переходу на конкретну сторінку.
- Зручність для невеликих наборів даних.

Недоліки:
- Можливе дублювання або пропуск подій під час оновлення каталогу.
- Зниження продуктивності при великих значеннях offset.

### Варіант 2. Курсорна пагінація

Використання параметрів `limit` та `cursor`.

Курсор визначає позицію останньої отриманої події.

Переваги:
- Стабільніший перегляд каталогу при додаванні нових подій.
- Ефективна робота з великими наборами даних.
- Відсутність необхідності пропускати велику кількість записів.

Недоліки:
- Неможливість прямого переходу на довільну сторінку.
- Складніша реалізація.
- Необхідність стабільного сортування.

## Рішення

Для каталогу EventHub обрано курсорну пагінацію.

Курсор формується на основі полів `startsAt` та `id`.

Поле `startsAt` визначає порядок подій за датою початку, а `id` забезпечує унікальний порядок для подій з однаковим часом початку.

API використовує параметри `cursor` та `limit`, а у відповіді повертає `nextCursor`.

## Наслідки

### Позитивні

- Зменшується ризик дублювання та пропуску подій при додаванні нових записів.
- Підвищується ефективність роботи з великим каталогом.
- Забезпечується стабільний порядок сортування.
- Спрощується реалізація послідовного завантаження подій.

### Негативні

- Неможливо безпосередньо перейти на сторінку з конкретним номером, наприклад на сьому.
- API не надає загальну кількість сторінок без додаткових обчислень.
- Запити до бази даних стають складнішими.
- Потрібно використовувати додатковий унікальний ключ сортування `id`.
- Необхідно правильно формувати та обробляти курсори.

## Висновок

Курсорна пагінація краще підходить для EventHub, оскільки каталог подій може постійно змінюватися.

Попри складнішу реалізацію та обмеження навігації, цей підхід забезпечує стабільніший перегляд даних і кращу масштабованість системи.
