
# ADR-005: Зберігання access-токена

**Статус:** Прийнято

## Контекст

Для автентифікації у EventHub використовуються короткоживучі access-токени та refresh-токени.

Необхідно обрати місце зберігання access-токена на клієнті.

## Розглянуті варіанти

### localStorage

Переваги:
- Токен зберігається після перезавантаження сторінки.
- Просте використання.

Недоліки:
- Токен доступний JavaScript.
- У разі XSS токен може бути викрадений.

### Пам'ять застосунку

Переваги:
- Access-токен не зберігається постійно.
- Після закриття вкладки токен зникає.

Недоліки:
- Після F5 потрібно відновити токен.
- Окремі вкладки мають власний стан.

## Рішення

Access-токен зберігається в пам'яті JavaScript.

Refresh-токен зберігається в httpOnly-cookie з
SameSite=Strict та обмеженим шляхом.

Після перезавантаження сторінки клієнт звертається
до /auth/refresh для відновлення access-токена.

## Наслідки

Покращується захист від тривалого зберігання
access-токена у браузері.

Необхідно реалізувати автоматичне оновлення сесії
та уникати паралельних запитів на refresh.

## Робота з кількома вкладками

Поточна реалізація використовує одну обіцянку
refreshInFlight у межах однієї вкладки.

Для синхронізації кількох вкладок у майбутньому
потрібен окремий механізм координації.

## Коли переглянути рішення

При появі складнішої багатовкладкової роботи
або зміні моделі автентифікації.
